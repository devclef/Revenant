# Crypto: Sealing, Unlocking and Time Lock

Loads only when working on crypto, the sealed format, or the routes that store letters and release time-lock secrets. The always-loaded summary is in `tech.md`. If anything here conflicts with it, stop and resolve the conflict before writing code.

## Goals

1. The operator cannot read a letter, its personal numbers or the recall answers.
2. Nobody can open a letter through Revenant before its opening date, even with the passkey or backup key.
3. After the opening date, the passkey or the backup key opens the letter, on any supported device.
4. Any change to a sealed letter is detected.

## Primitives

All from WebCrypto, in the browser. No custom crypto, no third-party crypto libraries.

- AES-256-GCM, random 96-bit nonce per encryption, never reused with the same key.
- HKDF-SHA256 for every derived key, each with its own `info` string.
- SHA-256 over RFC 8785 canonical JSON for the envelope hash.
- `crypto.getRandomValues` for all random values.

## Key hierarchy

```
DEK  (random 256-bit, encrypts the payload)
 ├─ wrapped by KEK_passkey = HKDF(ikm = PRF output ‖ serverSecret, salt = letterId, info = "revenant-kek-passkey-v1")
 └─ wrapped by KEK_backup  = HKDF(ikm = backupKey ‖ serverSecret,  salt = letterId, info = "revenant-kek-backup-v1")

Opening records key = HKDF(ikm = DEK, salt = letterId, info = "revenant-opening-v1")
```

- **DEK:** generated in the browser. Encrypts the payload with AES-256-GCM, with AAD set to the canonical envelope header.
- **Wrapped DEKs:** one per factor, each AES-256-GCM with AAD = `letterId ‖ factor name`.
- **serverSecret:** 256-bit random, generated by the server per letter. Released only when server UTC time is at or after `opens_at`. It is part of every KEK, so neither factor works before the date.
- **Opening records key:** encrypts recall answers, so the operator can't read those either.

## Passkey (WebAuthn PRF)

- RP ID comes from config (`RP_ID`), never from the request host. MVP and testing use `revenant.devclef.se`; local development uses `localhost`. The RP ID is stored in each envelope header so a letter always knows which domain its passkey belongs to.
- One new passkey per letter, discoverable (`residentKey: "required"`), `userVerification: "required"`. The user name shown in the passkey manager identifies the letter, for example `Revenant letter · opens 5 Nov 2030`. Demo passkeys are named `Revenant demo`.
- PRF input: a random 32-byte `prfSalt` per letter, stored in the header.
- The server does not verify WebAuthn assertions. The passkey is a key source, not a login. Security comes from the PRF output, which never leaves the browser.

### PRF check at sealing

Support depends on browser, OS and passkey provider, and some providers only return PRF on `get()`, not on `create()`. Never assume it works.

1. `create()` with the `prf` extension and `eval.first = prfSalt`.
2. `get()` with `allowCredentials = [credentialId]` and the same salt. Require a 32-byte `prf.results.first`.
3. If `create()` also returned a PRF result, require it to equal the `get()` result.
4. Wrap the DEK with `KEK_passkey`, then unwrap it again and compare.
5. If any step fails: tell the user plainly that this device can't lock the letter with a passkey, and require the backup key. Do not store a passkey wrap that failed the check.

If the check passes, the backup key is optional. Skipping it requires an explicit confirmation that a lost passkey means the letter can never be opened.

Sealing from a computer without a capable platform passkey should offer the browser's "use a phone or tablet" option, which can create the passkey on the phone. The sealing screen also explains that a passkey may not be usable on a device from a different ecosystem, and what to do instead (the "use a phone" option, or the backup key).

## Backup key

- 128-bit random, encoded as Crockford Base32 in groups of four, with a checksum so typos are caught before any decryption attempt.
- Generated and rendered into the backup key card entirely in the browser. It is never sent to the server, logged, stored, or put in analytics.
- The card always carries the letter link, as text and as a QR code with the key in the URL fragment (`/l/<letterId>#k=...`). Fragments aren't sent to the server. On load, the app reads the fragment, then removes it with `history.replaceState`. The fragment must never be written to logs, analytics, error reports or `Referer` headers (set `Referrer-Policy: no-referrer` on letter pages).
- 128 bits is enough on its own, because after the opening date the serverSecret is released to anyone with the letter ID.

## Envelope

Unencrypted header: `letterId`, `formatVersion`, `sealedAt`, `opensAt`, `rpId`, `credentialId` (if a passkey wrap exists), `prfSalt`, the wrapped DEKs with their nonces, the payload nonce, and the payload ciphertext. The envelope hash is stored alongside.

The header must not reveal what the letter contains or tracks.

## Sealing flow

1. Browser asks the server to prepare a letter. The server creates a draft with a random 128-bit `letterId` and a `serverSecret`, and returns both.
2. Browser builds the payload, generates the DEK, encrypts, runs the PRF check, wraps the DEK for each available factor, builds the envelope and computes its hash.
3. Browser sends the envelope. The server recomputes the hash, checks `opensAt` against the allowed range for real or demo letters, and stores the letter as sealed in one transaction. From then on the row is immutable.
4. Browser discards the DEK, serverSecret and PRF output from memory, then produces the letter card, backup key card and `.ics` file.
5. Unsealed drafts expire and are deleted after a short time.

## Opening flow

1. The letter link loads the header. Before `opensAt`, the API returns only `opensAt` and sealed status for the countdown.
2. At or after `opensAt`, the API returns the envelope and the serverSecret.
3. Browser verifies the envelope hash, derives the KEK from the passkey PRF output or the backup key, unwraps the DEK and decrypts. An AES-GCM failure means wrong key or tampering. Say which is likely, but never show partial data.
4. Recall answers are encrypted with the opening records key and stored before anything else is shown.

## Demo letters

- Persona letters are sealed by a script with a published demo backup key and an `opensAt` in the past. The persona page opens them with that key. Persona letters have no passkey wrap and never prompt for a passkey.
- Live demo letters use the real flow, including the PRF check, letter card and `.ics`, with `opensAt = sealedAt + 30 seconds`. The server accepts this only for the demo table.

## Threat model

| Threat | Protection | Accepted risk |
|---|---|---|
| Operator or database breach reads letters | Payload and opening records are encrypted. The server never sees the PRF output, backup key or DEK. | Metadata is visible: `sealedAt`, `opensAt`, letter count. |
| Author or someone with their key opens early | serverSecret is part of every KEK and is released only after `opensAt`. | The author knows what they wrote and could copy it before sealing. The lock stops early opening through Revenant, not memory. An operator or breach with the serverSecret can bypass the lock, but still needs a key. |
| Someone finds the letter card (QR) | The card holds only a link. Before the date: countdown. After: still needs passkey or backup key. | They learn the opening date. |
| Someone finds the backup key card | Before the date: useless. | The card holds the link and the key, so after the date it alone opens the letter. Users are told to store it like a house key. |
| Stolen phone with the passkey | `userVerification: "required"` needs fingerprint, face or PIN. | A compromised or unlocked device. |
| Guessing letter IDs | 128-bit random IDs. Rate limiting is added later. | No rate limiting in the MVP, even though the cluster is internet-facing. 128-bit IDs make guessing impractical; the main exposure is spam letters. |
| Tampering with sealed data | Database triggers block updates and deletes; envelope hash; AES-GCM tags. | Deletion by the operator (availability, not integrity). |
| Malicious or injected JavaScript (XSS, compromised dependency, malicious deploy) | Strict CSP, no third-party scripts or analytics on sealing and opening pages, pinned lockfile, minimal dependencies. | This is the main residual risk. Browser crypto is only as trustworthy as the code the server serves. |
| Lost passkey, deleted passkey, or PRF inconsistency across devices | Backup key card; PRF check at sealing. | The backup key is optional. A user who skipped it and loses the passkey loses the letter forever. |
| Domain changed (MVP runs on `revenant.devclef.se`) | RP ID stored in each header. | Passkeys only work on their original domain. On a new domain, only the backup key opens older letters. |
| Revenant shuts down | | Accepted for MVP: letters can't be opened. |

Out of scope: coercion of the user, compromised operating systems, nation-state attackers.
